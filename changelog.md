This release brings the following changes:
* Keep the NVDA log free of the deprecation warnings NVDA 2026.3 writes, with a full stack each time, when an add-on uses the old names of its braille extension points and gesture classes. They are now taken from where each version of NVDA keeps them, so NVDA 2024.1 to 2026.3 all load the add-on without a word in the log.
* Stop filling the NVDA log with warnings about ordinary events: a remote sound arriving late is reported once per stream instead of at every gap, a peer without end-to-end encryption (an older TeleNVDA or the official NVDA Remote client) and a switch to another transport are information, not warnings, and a relay which cannot be reached is reported once, its retries staying in the daily log. A failed connection no longer leaves an error about a certificate fingerprint which could not be read, since no certificate was received at all.
* Announce NVDA 2024.1 as the oldest supported version. The add-on needs the Python of NVDA 2024.1 and later, so older versions could install it but not load it.
* Hide the content of a session from the relay. The relay used to read everything it forwarded: speech, braille, keystrokes, the clipboard, the sound. Two up to date computers now agree on keys of their own as soon as they meet on a channel, through the relay but without it ever holding them, and seal every message with them; the relay, its logs and its database only see who joined and who left. Nothing changes for the users: the channel key still opens the session, the session password still works as before and takes precedence, and an older add-on or the official NVDA Remote client is still served, in which case the session simply stays as readable as it was.
* Fall back to HTTPS long polling when a gateway holds back the streaming response. Gateways which scan whole responses, such as McAfee Web Gateway, never forward even the headers of a response which does not end, and the connection timed out every few seconds for ever instead of switching to the long polling which works through them.
* Hide the F15 key of the keep awake from NVDA on the controlled computer, instead of cutting speech around it. Every minute without a key press, it turned speech off for half a second around its F15 key, and NVDA drops whatever it is asked to say meanwhile: a say all or a long reading stopped in the middle. Worse, speech turned off on the controlled computer is precisely what gets relayed to the controlling one, so with input help or command key reporting on, "F15" was heard on the controlling computer every minute, and shown on its braille display. The key is now injected the same way as keys which bypass NVDA: NVDA never sees it, nothing is said, shown or relayed, and speech is never touched. It is sent whenever Windows has seen no input for the delay, including while NVDA speaks or reads, so the screen no longer locks in the middle of a long reading. Speech, braille display gestures, a file transfer and a shared screen or sound count as activity: they restart the maximum duration, like a key press does, and once that duration is over, the first key press or mouse move arms the keep awake again instead of leaving it off until the next connection.
* Switch to the classic HTTPS transport when the network refuses WebSocket. Gateways such as McAfee Web Gateway let HTTPS through but answer the WebSocket handshake with an error page of their own, and TeleNVDA met that same refusal every five seconds for ever, logging the whole page each time. Both the controlled and the controlling computer now reconnect over HTTPS at once, say so once, and keep HTTPS in their settings when the refused relay is the one saved there, so the next start goes straight to it. A proxy asking for credentials or an unreachable relay is not taken for such a refusal.
* Tell the user of the computer to be controlled when the relay cannot be reached. That side registered no callback at all for a failed connection: it retried every few seconds for ever, without a sound or a word, so a session which could never start looked exactly like one which was about to. It is now announced once, and the attempts continue quietly.
* Say why a connection attempt failed. The connector retried every few seconds without a word, in the NVDA log or anywhere else, so a relay which refused the connection looked exactly like a relay which was never called. The first failure is now reported with its traceback, the following ones in one line, and every attempt is recorded in the daily log.
* Let the modules of the add-on be heard. NVDA gives them no log level of their own, so they inherited the one which throws away everything below a warning: the address dialled, the proxy used and the channel joined were written nowhere. They now speak down to their debug messages, into the daily log.
* Say in the NVDA log where the daily log is written, or why it is not written at all. An add-on directory which cannot be written to simply had no log and no way of telling why.
* Remove the `TeleNVDA` and `Remote` add-ons when this one is installed, instead of leaving two remote control add-ons fighting over the same gestures and the same relay. The add-ons removed are named to the user, and NVDA completes their removal at the restart it asks for anyway. An add-on NVDA can no longer read, or whose removal failed before, has its directory moved out of the way as well.
* Keep one log file per day in the `log` directory of the add-on, next to the add-on itself, holding the WebSocket and classic HTTPS traffic along with the warnings and the errors of TeleNVDA. NVDA rewrites its own log at every start, which left nothing to look at when a session had misbehaved the day before. Only the direction, the type and the size of the relay messages are recorded, never their content, which carries speech, braille and keystrokes. Nothing is written on a secure screen, the files older than thirty days are deleted, and the history survives an update of the add-on. The `[logging]` section of `teleNVDA.ini` turns the log or its message by message part off and sets how long the files are kept.
* Upgrade classic HTTPS relay connections to streaming v2 when available, with
	automatic fallback to v1 long polling. The HTTPS relay version and v2 path
	can be selected in the advanced TeleNVDA options; automatic mode is
	recommended, while manual selection is intended mainly for diagnostics.
* Add an optional classic HTTPS long-polling relay transport for enterprise
	proxies that allow ordinary HTTPS but block WebSocket. The transport uses
	the same TLS protection and relay authentication, with a default API path of
	`/remote/http/v1`; it is selected explicitly and is not an automatic
	WebSocket fallback.
* Keep the last-used relay and the built-in relay list when switching from Client to Server and back in the connection dialog.
* Remember the last 10 successful connection keys by default, with a per-user setting in the TeleNVDA options to choose how many keys are retained.
* Open the list of the applications heard by pressing the remote audio gesture twice, from either computer, and act on the session in progress rather than only on a preference. Silencing an application while it is being heard used to mean going into the options and starting the session again for the choice to be applied.
* Write in the log of NVDA what remote audio is doing: which applications hold a sound session on the computer being heard, which of them are captured, what is announced to the listening computer and what the Audio sources dialog was given. Those modules wrote to a log of their own which NVDA never reads, so nothing they had to say was recorded anywhere.
* Fix an application added by hand in the Audio sources dialog always being announced as not running, even when it was playing at that very moment.
* Say the truth when asking permission to share the sound on a Windows too old to separate the applications: the question now states that everything played there will be heard, the speech of that screen reader included, instead of promising that only the applications will be.
* Say how many relay addresses were really offered for screen sharing, and name them in the log. The count given until now was the number of groups the relay sorts them into, always one or two, which made a correctly configured relay look as though it were offering less than it was.
* Take the invisible screen sharing window out of the task switcher of the computer being watched, and give the keyboard back to its user when a session starts. That window opened in the foreground and offered itself to every press of alt and tab, so their screen reader read them a page they could not see and their typing went into it instead of into their work.
* Say when the shared picture does not arrive, instead of leaving the controlling user in front of a window which stays black, and write in the log of NVDA what the screen sharing window actually did: which browser started, how many relay addresses were given, which kinds of address were found, how the link ended and at which size the picture arrived. Nothing of this was recorded until now, so a session which showed nothing left nothing to look at afterwards.
* Fix the controlling computer hearing nothing at all when the user of the controlled one had turned the speech of their NVDA off: what that NVDA was told not to say is now sent to the controlling computer, while the controlled one stays as silent as its user asked.
* Add remote audio: the controlling computer can hear what the controlled one is playing with NVDA+Control+Shift+K. The sound is a session of its own and needs no screen sharing, no browser and no server other than the relay already in use. Each application is captured separately and mixed, so the speech of the controlled computer's own screen reader is never sent back. The sound is carried by the messages of the session itself, and is therefore encrypted along with everything else when an encryption password is set; it costs about a hundred and seventy kilobits a second. The Audio sources button in the options lists the applications heard and lets any of them be silenced; only the refused ones are remembered, by program name. The controlled computer asks its user before anything is heard. On Windows older than version 2004, which cannot separate one program's sound from another's, the whole sound card is shared instead and both users are told.
* Add screen sharing: the controlling computer can display the screen of the controlled one with NVDA+Control+Shift+V, and move its mouse when the controlled computer allows it. The picture travels directly between the two computers rather than through the relay server. The controlled computer asks its user before anything is shared, mouse control is refused by default, and no keyboard input is ever sent this way. The feature requires a relay started with screen sharing enabled and is simply never offered otherwise.
* Add a chunked file transfer which is no longer limited to 10 MB when both computers run a version of TeleNVDA which supports it. Transfers work in both directions, report progress, transferred size, speed and estimated remaining time, can be cancelled from either end, and the received file is verified with a SHA-256 checksum before being saved.
* Negotiate the available features when the connection is established, so that computers running the original TeleNVDA or the standard NVDA Remote automatically fall back to the legacy 10 MB transfer.
* Add an option to send files larger than 10 MB to computers which only support the legacy transfer, and an option to limit the size of received files.
* Handle server connections which break when client sends ALPN information. This should restore connectivity to nvdaremote.com and similar servers.
* Add native Windows SSPI authentication for NTLM and Kerberos/Negotiate HTTP proxy CONNECT handshakes used by WebSocket relays.
* Check GitHub Releases for TeleNVDA stable updates at startup or on demand, with SHA-256 verification and confirmation before installation.
* Fix automatic updates that failed to complete with an "access denied" error by marking the previous version for removal before installing the downloaded package, and recover installations that were already stuck pending.
* Automatically trust and remember previously unknown server certificate fingerprints so manual and automatic connections are not blocked by a confirmation dialog.
* Add a configurable inactivity timeout for automatic connections and a configurable folder for received screenshots.
* Add keyboard gestures for remote screenshots: NVDA+Control+Shift+P for the native capture and Windows+Alt+P for the PowerShell capture. Both work from the controlling and the controlled computer.
* Fix the PowerShell screenshot request, which silently used the native capture method instead.
* Fix the PowerShell screenshot request, which did nothing when the controlled computer ran a standard TeleNVDA: the capture method is now sent as a parameter of the usual screenshot request, so those computers answer with their native capture instead of ignoring the request.
* Make the PowerShell screenshot work with a controlled computer running the NVDA Remote add-on shipped with NVDA or the original TeleNVDA: when nothing answers the screenshot request, the capture is driven through the clipboard and keyboard messages of the standard protocol. Known issue: this compatible capture does not work yet, the Run dialog is never opened on the controlled computer. It will be fixed in a later release.
* Fix the screenshot gestures, which were forwarded to the controlled computer instead of being handled locally while remote control was active.
* Fall back to the native capture when PowerShell is unavailable or blocked on the controlled computer, and run PowerShell from its absolute path so a restricted PATH no longer prevents the capture.
* Encode remote screenshots as JPEG instead of the raw bitmap before Base64 encoding, so that captures transfer faster.
* Add proxy settings to the connection dialog, with a proxy mode which can be manual, automatic Windows detection or no proxy. Existing configurations left in manual mode without a proxy address are switched to automatic detection.
* Fix the proxy settings of the connection dialog, which were forgotten as soon as the dialog was validated and had to be entered again after each restart of NVDA. The one-off conversion of manual configurations without an address no longer discards the chosen mode at every start.
* Fix NTLM and Kerberos/Negotiate proxy authentication with proxies which return an error page along with their challenge, such as Squid: the page was left in the connection and read as the answer to the next authentication step, so the tunnel failed with an invalid response instead of opening.
* Use the proxy declared by Windows or by the environment for every kind of connection, including the classic HTTPS relay and the update check. A machine which declared its proxy only that way was reached through it over WebSocket but directly, and therefore not at all, over HTTPS.
* Remember the transport and the WebSocket path chosen in the connection dialog, which were only ever saved from the add-on settings until now.
* Fix screen sharing over the WebSocket transport, which never obtained the addresses of the relay servers and therefore failed to establish the picture between two computers on different networks, while the same session worked over the direct transport.
* Remove `url_handler.exe` from the add-on: `nvdaremote://` and `telenvda://` links are now opened through the URL handling NVDA already provides, so no executable is shipped any more and anti-virus software has nothing left to flag. This part of the feature requires NVDA 2025.1 or later; on older versions the links are simply not registered.
